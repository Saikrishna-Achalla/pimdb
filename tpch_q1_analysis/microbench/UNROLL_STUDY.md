# Loop-unrolling study: cuDF-style group-by aggregation kernel (TPC-H Q1 model, RTX 5070)

Scope: **unrolling only**. Atomic flavour (generic `ATOM.E.ADD.64.STRONG.SYS` into the shared-memory
table), launch (240 CTAs x 128 threads), table layout and per-kernel work are the same in every variant.
Code: `unroll_study.cu` (build: `./build_unroll_study.sh`, same toolchain/flags as `build.sh`).
Raw data: `unroll_study_results.txt` (11 column specs x 71 variants, all sums verified `OK` against the
CPU reference, 0 mismatches), `ncu_study/` (ncu `--set full`, every variant once, for LLLLL / IIIII /
LLLLLCC: `*.ncu-rep`, `*.json`, `*_table.txt`), `sass_study/` (full SASS dump, `sassops.py`,
`load_atom_order.txt`). Tables below are generated by `make_study_tables.py`.

Method: 3,153,518 rows with the real Q1 group ids (`q1_groups.csv`); CUDA events, median of 30 reps
(+5 warm-up), 96 MB memset between reps to flush L2. Event timer granularity on this driver is ~2 us.
Column spec letters: `L` = SUM int64 (8 B), `I` = SUM int32 (4 B), `C` = COUNT (no value load).
"% of 672" = input bytes / time / 672 GB/s. "ncu" columns come from one profiled launch with locked clocks.

## Recommendation

1. **Unroll across rows, not columns.** Each thread takes U rows per batch; per batch: issue the U slot
   (group-id) loads, then per column (runtime loop, type dispatch once per batch) issue U value loads and
   then U atomics. Column unrolling only helps when C is large and needs all columns in one batch
   (`cols ALL`); a partial `CU=2/4` + remainder gives 1.06-1.15x where rows U=4 gives 1.39x. Rows x columns
   adds registers and code and no time over rows alone.
2. **Mapping: warp-striped** (`row = tile + r*blockDim + tid`). Warp-striped, block-striped (grid) and
   thread-contiguous are within noise of each other at the recommended U; warp-striped has the simplest
   tail and no alignment requirement. Thread-contiguous with explicit 128-bit loads (`LD.E.128`) cuts
   load requests 591k -> 345k and warp-instructions by 18-31% but does not change time (the kernel is
   DRAM-bound at that point), and plain thread-contiguous degrades badly at U=16.
3. **U by column width: about 24-32 bytes of value loads in flight per thread: U=4 for 8-byte columns,
   U=8 for 4-byte columns** (U=3 / U=6 are already on the plateau). One kernel with U=8 is also fine for
   8-byte columns in this model (64 regs, same time as U=4). Stay at or below ~100 registers/thread
   (5 CTAs x 128 threads x 102 regs = one SM's register file): U=12 (96 regs) is still on the plateau,
   U=16 (116-124 regs) drops achieved occupancy from 41% to 27-30% and loses 7-34%.
4. **Unroll the slot loads together with the value loads** (up front, same batch). Loading the slot
   lazily next to its atomic costs up to 30% on narrow / few-column inputs.
5. **Tail: predicate (`row < n`) rather than a remainder loop** by default: same time on the stack-passed
   model, 6.8 KB vs 38.9 KB of code (U=4). One exception measured: with global descriptors, int32
   columns and U=4 the remainder-loop version is faster (149 vs 194 us, IIIII).
6. **Expected gain on the modeled kernel** (event-timed): 5 x int64: 349.9 -> 251.6 us, **1.39x**
   (U=4; 1.38x at U=8); Q1-shaped 7 dispatched columns with 2 that do no load (LLLLLCC): 380.6 -> 253.4 us,
   **1.50x**; 5 x int32: 309.0 -> 149.2 us, **2.07x** (U=8). With descriptors in global memory (`gdesc`,
   closer to cuDF): 321.2 -> 241.4 us (**1.33x**, LLLLL), 331.2 -> 241.4 (**1.37x**, LLLLLCC),
   290.5 -> 136.9 (**2.12x**, IIIII). Under ncu the plateau is 604-618 GB/s of DRAM traffic,
   i.e. 90-92% of the 672 GB/s peak; nothing unrolling-related is left above that.

## Variants

| name | what is unrolled |
|---|---|
| `baseline` | none: grid-stride, one row per iteration, runtime column loop, load -> atomic (same as `groupby_unroll_bench.cu`) |
| `naive pragma rows/grid/cols` | `#pragma unroll` only, no restructuring: U copies of the row body (warp-striped), the grid-stride loop itself, or the runtime column loop |
| `rows U=k warp` | k rows per batch, warp-striped; k slot loads; per column k loads then k atomics; predicated tail |
| `rows U=k thread` / `threadvec rem` | thread-contiguous rows (`row = gtid*k + r`); `threadvec` loads them as aligned 16-byte structs; remainder loop |
| `rows U=k grid` | block-striped: the baseline's own rows, k grid-stride iterations per batch |
| `... rem` | unpredicated main loop + one-row remainder loop instead of `row < n` predication |
| `... lazyslot` | value loads unrolled, slot load issued next to its first atomic (slot loads effectively not unrolled) |
| `... defslot` | slot loads up front, but their first use hidden until the atomics so slot and first-column loads overlap |
| `... minb5` | `__launch_bounds__(128, 5)` |
| `... sub64=s` | int64 columns processed in sub-batches of s rows inside the U-row batch (per-width U in one kernel) |
| `cols CU=k (U=1)` | k columns per batch (two dispatch passes: loads, then atomics), remaining columns one at a time |
| `cols ALL` | all columns, column loop fully unrolled to MAXC=8 and predicated on `j < C` |
| `both U=k x CU=m / ALL` | rows x columns batch |
| `gdesc ...` | same kernels, but column descriptors (kind, data pointer) are read from global memory on every access instead of from the by-value kernel parameter (cuDF reads its `column_device_view`s from global memory) |

- The rule's shape is confirmed: the knee depends on U x width, not on U, and is the same for C = 1, 2, 5, 7.
  Its constant is low by about 2x: 10 KB/SM (U=2 for int64) is not enough, the plateau starts at
  ~15 KB/SM and is flat by ~20 KB/SM, presumably because threads are not issuing loads while they execute
  their batch of atomics and the dispatch (not verified directly).
- Plateau: U=3..12 for int64, U=6..12 for int32 (regs 40..96).
- Fall-off: U=16 (124 regs by value, 116 gdesc): ncu occupancy 26.7-30.0%, 1.25 waves, time +7..15% vs
  plateau by value (gdesc: +8..34%, worst on a single int32 column). U=24/32 (168/244 regs, occupancy 22% / 15%) are erratic: on LLLLL they come back to within 1-3%
  of the plateau (fewer threads, each with more loads in flight), on int32 they stay 10-22% off.
- `__launch_bounds__(128, 5)` caps U=16/24/32 at 96 regs by spilling to local memory (SASS for U=16: 32 `STL`
  + 15 `LDL.LU` added). Event-timed it is slower than not capping (LLLLL U=16: 282.3 vs 269.8 us;
  U=32: 298.7 vs 259.8), while the single ncu launch shows the opposite for U=16 (234.4 vs 242.5 us) and
  agrees for U=24/32. Not a reliable way to extend the plateau; on U=8 it has no effect on time (regs 64 -> 78).


- **Aliasing / hoisting.** The compiler never moves a value load above a generic atomic. The baseline
  already has its runtime column loop auto-unrolled 4x by nvcc (`UISETP.GE.U32 UR4, 0x4`, `IADD R12, R12, 0x4`),
  and `#pragma unroll 4` on it produces the identical 616-instruction function: load, ATOM, load, ATOM.
  `#pragma unroll` over rows keeps even the `__restrict__` slot loads behind the previous row's atomics
  (SLOT at 0x490, 0x2500, 0x4570). All three pragma-only variants time at 0.99-1.00x. The loads have to be
  moved in the source.
- **Loads of column c+1 do not overlap atomics of column c** unless the source batches columns (`CU`,
  `ALL`): in `rows U=4` the next column's `LDL.64` + 4 loads (0x0d00..0x0dd0) come after the 4 ATOMs of the
  previous column. Batching them (`both`) works in SASS but buys no time once U x width >= 24-32 B.
- **Slot use is hoisted above the value loads.** In `rows U=4 warp` the compiler computes `slot * C`
  (`@!P1 IMAD R33, R6, R13` at 0x530..0x560) right after the slot loads and before any value load, so every
  batch waits once on the slot loads and then once per column. `defslot` moves that IMAD to 0x810, after the
  four `LD.E.64`; no time difference at U >= 4.
- **No automatic load widening.** Thread-contiguous rows stay 4 separate `LD.E.64`; only the explicit
  16-byte struct load gives `LD.E.128` (2 per 4 int64 rows, 1 per 4 int32 rows).
- **Predication** compiles to predicated loads (`@!P0 LD.E.64`), not branches.
- **Stack frame.** With by-value descriptors and a runtime column index, nvcc spills the descriptor struct
  to local memory (13 `STL.64` at entry, `LDL` kind + `LDL.64` pointer per row x column in the baseline, once
  per batch x column in `rows`). `cols ALL` indexes with constants, so the spill disappears (descriptors come
  from the constant bank via `LDCU`, loads become `LDG`).

## How a real implementation would pick U

- U must be a compile-time constant (register arrays). Two instantiations cover the measurements:
  U=4 and U=8, selected on the host from the narrowest aggregated value column (8 B -> U=4, <= 4 B -> U=8);
  1- and 2-byte columns were not measured. In this model a single U=8 kernel is as fast as U=4 on int64, so one
  variant suffices if the register budget allows.
- Cost in this model: regs 38 -> 40 (U=4) / 64 (U=8); code 9.6 KB -> 6.8 KB (U=4) / 11.6 KB (U=8) per kernel
  with a 3-way type switch (the unrolled kernels are not larger because nvcc stops auto-unrolling the column
  loop 4x). Code grows ~1.5 KB per unit of U (U=16: 23.6 KB, U=32: 47.4 KB) and linearly in the number of
  switch arms that carry a load, so with cuDF's ~25-arm type dispatch the per-U cost will be several times higher.
- Register budget rule for this launch shape: regs <= 65536 / (5 CTAs x 128 threads) = 102.

## Limits

- **Model gap.** The real kernel executes ~5x more warp-instructions per row than this model (5.09e7 vs
  ~1e7) at 72 regs and 32% achieved occupancy, and runs at 89 GB/s, far from DRAM-bound. Here the baseline
  is already at 56-59% of DRAM peak, so unrolling quickly hits the DRAM ceiling; in the real kernel the
  ceiling is further away but the per-row x column compute that unrolling does not remove is larger. The
  1.3-1.5x (int64) figure is the gain on the load -> atomic core only. What should transfer: the compiler
  will not reorder loads past the generic atomics, so the batch has to be written in the source; rows are the
  right axis; U x width ~ 32 B; keep regs under the one-wave limit (the real kernel starts at 72, so U=4 is
  the safer choice there and U=8 may not fit under 102). What may not: the real per-element path (validity,
  aggregation-kind dispatch) must itself be made batchable, and its extra registers per row are unknown.
- **Stack-frame confound.** The by-value-descriptor kernels carry a local stack frame; with n = 1000 rows
  the launch costs 10.0-11.7 us (baseline) vs 3.8 us (`cols ALL`, no frame) vs 7.9 us (`gdesc baseline`). That
  fixed ~8 us is why `cols ALL` / `both U=2 x ALL` look 4-6% better than `rows` in event time on LLLLL
  (240.8 vs 251.6 us) while ncu kernel durations are equal (228.8 vs 231.4-235.5 us). With descriptors in
  global memory, `gdesc rows U=6` is within 3% of the best column / rows x columns variant on every spec
  and far ahead of `cols ALL` on 1-2 column and int32 inputs.
- Event times (launch + kernel, right after a 96 MB memset) and ncu durations (kernel only, locked clocks,
  single sample) differ by up to ~60 us in both directions (IIIII baseline: 309.0 us event vs 372.4 us ncu; LLLLL U=8:
  253.7 vs 231.4); rankings agree except where noted.
- Not explained: `gdesc both U=2 x ALL` is slow (292.5 us LLLLL vs 241 for its neighbours); `gdesc rows U=4`
  on int32 is slower than U=3 and than its own `rem` version; `rows U=16 thread` is much slower than
  `rows U=16 warp` (341.7 vs 269.8 us). Sectors-per-request was not collected.
- Grid/block size was held at 240 x 128 throughout; the U thresholds scale with threads per SM.

Other optimization, not implemented (out of scope): the per-row x column dispatch/descriptor overhead that
makes the real kernel 5x heavier than this model is likely a bigger lever than the load -> atomic overlap.
